# 종목 즐겨찾기 인원 표시 설계

- 작성일: 2026-09-17
- 브랜치: `feature/stock-favorite-count` (시작 커밋 `e3aec16`, 기존 변경 보존)
- 범위: 설계 및 Claude CLI 리뷰 완료 후 사용자 요청으로 기능 코드 수정 완료. 테스트는 사용자가 진행하며 커밋·배포는 진행하지 않음.
- 현재 구현 기준: 아래 **코드 리뷰 반영 설계 v2**. 앞의 설계/리뷰는 배경이며 충돌 시 v2를 우선한다.

## 요구사항

- 종목 상세 별 아이콘 왼쪽에 숫자만 표시한다. 예: `1,234 ★`, 실제 집계가 없으면 `0 ☆`.
- 비회원도 집계는 조회할 수 있지만 상세·종목 카드 모두 즐겨찾기를 변경할 수 없다.
- 로그인 회원의 추가·해제 성공 후 서버 집계를 다시 조회한다.
- 실패, 중복 클릭, 로그인 동기화, 로그아웃 이후 늦게 도착한 응답을 처리한다.
- 다른 회원의 변경을 실시간으로 전송하는 WebSocket/주기적 폴링은 도입하지 않는다.

## 서버

- `FavoriteRepository.countByStock_Code(code)`로 기존 테이블을 집계한다. `(member_id, stock_code)` 유일 제약으로 한 회원당 한 행이다.
- `FavoriteService`에 읽기 전용 집계 메서드와 count 응답 DTO를 추가한다.
- `GET /api/favorites/{code}/count` → `{ "count": 123 }`. 이 GET 경로만 공개한다. 목록·추가·삭제 인증은 유지한다.
- SecurityConfig에서 `requestMatchers(HttpMethod.GET, "/api/favorites/*/count").permitAll()`을 `anyRequest()`보다 앞에 배치한다. `/api/favorites/**` 전체 공개는 하지 않는다.
- 집계 엔드포인트는 일치하는 행이 없으면 0을 반환한다. 종목 자체의 유효성 안내는 기존 상세 조회가 담당한다.
- 별도 집계 컬럼이나 Redis 캐시를 만들지 않는다. 실제 DB의 stock_code 인덱스 유무를 구현 때 확인한다. 회원 ID로 시작하는 복합 유일 인덱스만으로 종목별 조회가 최적화된다고 가정하지 않는다.
- 기존 `exists → save`는 동시 요청에서 유일 제약 오류가 날 수 있다. PostgreSQL `ON CONFLICT (member_id, stock_code) DO NOTHING` 방식의 원자적 추가를 사용한다. 생성·수정일 등 필수 컬럼도 구현 시 확인한다. 실패한 트랜잭션 내부에서 예외만 삼키지 않으며, 관계 오류 등 다른 제약 위반을 성공으로 처리하지 않는다.

## 프론트엔드

- React Query 패키지는 있으나 현재 `QueryClientProvider` 사용이 없어, 기존 Zustand 구조를 활용한 즐겨찾기 전용 상태/액션으로 관리한다.
- 종목별 집계·로딩·오류·요청 세대와 계정별 동기화 상태, 종목별 변경 요청 상태를 구분한다.
- 상세 진입 시 집계를 조회한다. 성공한 추가·삭제는 상세/카드 어느 곳에서 발생해도 해당 종목 집계를 재조회한다.
- 초기 로딩은 스켈레톤, 조회 실패는 `—`와 재시도 안내로 표시한다. 실패를 0으로 표시하지 않는다. 이전 수치가 있으면 갱신 실패 상태를 함께 표시한다.
- 별 버튼은 비회원, 목록 동기화 전/실패, 해당 종목 변경 요청 중에 비활성화한다. 비회원은 빈 별과 로그인 필요 설명을 제공한다. 공통 훅 내부에서도 인증을 검사한다.
- 요청 전에 공유 상태에서 동기적으로 잠금 처리해 같은 종목의 여러 훅 인스턴스/빠른 연속 클릭을 막는다. 다른 종목은 독립적으로 처리한다.
- 서버 변경 성공 후 즐겨찾기 여부를 명시적으로 설정한다. 단순 로컬 toggle을 재실행하지 않는다. 실패 시 기존 상태와 오류 안내를 유지한다.
- 변경 성공 후 집계 재조회 실패는 별도의 오류이다. 성공한 변경을 되돌리지 않는다. 통신 단절로 성공 여부가 불명확한 경우 목록을 재동기화한다.
- 로그아웃/계정 전환 뒤 이전 응답이 상태를 덮지 않도록 세션 세대를 확인한다. 잠금 해제도 요청 식별자를 확인한다.
- `useAuthStore`에 메모리 전용 `authGeneration`을 두고 인증 초기화·로그인·로그아웃 시 증가시킨다. 목록 동기화와 변경 요청은 시작 시 세대를 캡처하고 성공·실패·finally에서 현재 세대 및 요청 ID가 같은 경우에만 계정 상태를 반영한다. 공개 집계는 종목별 요청 순번으로 오래된 응답을 무시한다.
- 서버 변경 완료 후 해당 요청의 잠금을 해제한다. 집계 재조회는 별도 로딩/오류로 관리한다. 변경 타임아웃 등 결과가 불명확하면 목록 재동기화가 완료될 때까지 해당 계정의 변경을 막고 재시도를 제공한다.

## 기존 로컬 즐겨찾기 정리

- `favoriteSync.ts`의 로컬 목록 자동 업로드를 제거한다. 빈 배열을 포함해 서버 목록을 기준으로 삼는다.
- `gaemi_watchlist`를 초기 상태/자동 등록 근거로 사용하지 않는다. 계정 즐겨찾기는 메모리에 보관하고 로그인 시 조회한다.
- 로그인 초기화의 중복 조회를 병합하며, 늦은 목록 조회가 성공한 변경을 덮지 않도록 동기화 완료 전 변경을 막고 응답 세대를 검사한다.
- 로그아웃·세션 만료·탈퇴에서 계정 목록을 초기화한다. 인증 전체 구조의 재설계는 범위에 포함하지 않는다.

### 2. 상태 소유와 변경 파일

- `useAppStore.ts`: 기존 소비자가 쓰는 `watchlist`는 유지하되 메모리 전용으로 전환. localStorage 로드/쓰기와 `toggleWatchlist`를 제거하고 `setWatchlist` 및 종목별 명시적 추가/삭제 액션만 사용한다.
- 새 `useFavoriteStore.ts`: 인증과 독립된 상태 저장소. `ownerGeneration`, `syncStatus`(idle/loading/ready/error/reconciling), 동기화 요청 ID, 종목별 pending/request ID/error, 공개 count 상태를 가진다. 이 저장소는 `useAuthStore`나 API를 import하지 않는다.
- `useAuthStore.ts`: 메모리 전용 `authGeneration`을 관리한다. `init`에서 실제 자격증명이 바뀔 때, `setAuth`, `clearAuth`에서 세대를 증가시키고 이전 목록/변경 상태를 동기적으로 초기화한다. 반복된 같은 자격증명의 init은 상태를 초기화하지 않는다. reset 액션은 공개 count와 계정 상태를 구분한다.
- 의존 방향은 auth → 단순 상태 저장소, favoriteSync/useFavorite → auth·상태·API로 한정해 순환 import를 피한다.
- `favoriteSync.ts`: 목록 조회·중복 조회 병합·세대 검증 담당. 예전 로컬 자동 업로드와 시세 조회는 삭제한다.
- `AuthStoreInitializer.tsx`: 인증 세대 변화를 구독해 로그인 세대마다 목록 동기화를 시작하는 단일 진입점으로 바꾼다. 인증 초기화 완료 및 `isLoggedIn`일 때만 요청하며 비로그인에서는 호출하지 않는다. `login/page.tsx`의 일반/Google 로그인 직후 별도 동기화 호출은 제거한다. Strict Mode의 같은 세대 중복 호출은 진행 중 Promise로 병합한다.
- `Sidebar.tsx`: 별도 목록 초기화를 공통 clearAuth로 통합. 세션 만료·탈퇴도 같은 초기화 경로 사용. `gaemi_watchlist` 잔존 키는 제거하되 다른 저장값을 지우지 않는다.
- `useFavorite.ts`: 클릭 자격 검사·요청 잠금·성공/실패 처리. 기존 카드/상세 소비 인터페이스에 pending·error·retry 상태를 추가한다.
- `favoriteApi.ts`: 공개 count 조회 추가. 회원 요청은 시작 시 캡처한 토큰을 명시적으로 전달한다. 공통 `api.ts` 인터셉터는 이미 명시된 Authorization을 덮지 않게 최소 수정한다. 명시 헤더 없는 기존 호출 동작은 유지한다. 계정 응답 검증과 실제 전송 토큰의 주체가 일치해야 한다.

### 3. 상태 전이와 경합 처리

1. **로그인/초기화:** 세대 증가 → 계정 목록/요청 상태 초기화 → 목록 조회(loading) → 같은 세대·조회 ID일 때만 목록 적용(ready). 실패 시 error와 재시도 제공. 조회 완료 전 별 변경은 불가하다.
2. **클릭:** 현재 로그인·ownerGeneration·ready·해당 code의 pending 없음 확인 → 목표 상태(add/remove)를 한 번 결정 → 공유 잠금을 동기적으로 설정 → 캡처한 토큰으로 요청한다. 같은 code는 중복 전송하지 않고 다른 code는 독립적으로 처리한다.
3. **명확한 성공:** 세대·요청 ID 확인 → 목표 상태를 명시적으로 적용 → 해당 잠금 해제 → 해당 code의 count를 새 요청 ID로 재조회. 성공한 저장을 count 조회 오류 때문에 되돌리지 않는다.
4. **명확한 거절(4xx):** 기존 별 상태 유지, 오류 안내, 잠금 해제. 401은 해당 세대가 여전히 현재일 때만 clearAuth. 현 설정의 익명 접근은 403일 수도 있으므로 모든 403을 강제 로그아웃으로 취급하지 않는다.
5. **응답 소실/타임아웃/5xx:** 실제 DB 반영 여부가 불명확하므로 계정 상태를 reconciling으로 전환해 새 변경 요청을 막는다. 이미 시작된 다른 종목 요청의 완료까지 기다린 뒤 목록을 다시 조회한다. 이전에 시작된 목록 조회는 적용하지 않는다. 재조회 실패 시 error·재시도 유지. 성공 시 서버 목록을 적용하고 영향을 받은 count를 다시 조회한다.
6. **로그아웃/계정 전환:** 즉시 세대 변경·목록/계정 요청 상태 초기화. 이전 요청은 네트워크에서 끝나더라도 success/catch/finally에서 현재 계정 상태를 변경하지 않는다. 오래된 finally가 새 요청의 pending을 해제하지 못하게 요청 ID도 비교한다.
7. **집계 경합:** count는 계정 정보가 아닌 종목별 공개 값. 종목별 증가 요청 ID로 이전 응답을 버린다. 저장 후 조회는 이전 진행 중 조회를 재사용하지 않는다. count 실패는 초기에는 `—`, 기존 값이 있으면 갱신 실패 표시와 재시도를 제공한다.

재동기화 한 번이 서버에서 아직 실행 중인 타임아웃 요청의 커밋까지 보장하지는 않는다. 이번 범위는 정상 응답 후 일관성과 이후 조회를 통한 복구이며, 통신 단절 상황의 강한 순서 보장이 필요하면 서버 요청 ID/버전 프로토콜이 별도 필요하다. 이 한계를 테스트·설명에서 숨기지 않는다. 여러 탭의 반대 방향 추가·삭제 역시 서버 처리 순서 기준이며 전역 클릭 순서를 보장하지 않는다.

### 4. 서버 처리 구체화

- 집계: 기존 공개 GET count 설계 유지. Security matcher는 GET `/api/favorites/*/count`만 공개. `long` DTO 필드 사용.
- 추가: 서비스 트랜잭션에서 회원·종목을 확인한 뒤 repository의 modifying native insert 실행. 실제 테이블/컬럼 매핑을 확인하고 `member_id, stock_code, stock_name, created_date, modified_date`를 명시한다. ID는 기존 identity를 사용한다.
- native SQL은 JPA auditing을 실행하지 않으므로 기존 LocalDateTime 정책과 맞는 `now`를 애플리케이션에서 생성해 두 감사 필드에 동일하게 전달한다. 중복이면 기존 날짜·종목명은 변경하지 않는다.
- 충돌 대상은 `(member_id, stock_code)`로 지정하고 `DO NOTHING`. 반환 행 수 0/1 모두 기존 POST 성공 응답으로 처리한다. FK/NOT NULL 등 다른 제약 오류를 무조건 성공으로 바꾸지 않는다.
- 삭제: 해당 회원/종목 삭제, 이미 없으면 기존 204 유지. DB 유일 제약은 유지한다.
- 입력: 추가 시 stockName null/공백/길이 제한을 검증(실제 컬럼 길이 기준). 회원 부재 401·종목 부재 404는 즐겨찾기 서비스/컨트롤러의 명시적 상태 예외로 처리한다. 확인 직후 삭제되는 극단적 FK 경합까지 4xx로 보장한다고 주장하지 않는다.
- stock_code 단독 인덱스는 구현 시 실제 DB/스키마를 확인한 뒤 결정한다. 이번 설계만으로 운영 DDL을 실행하지 않는다.

5. 서버 관련 테스트와 프론트 정적 검사/빌드, 아래 상태 경합 검증 후 Claude 코드 리뷰를 요청한다.

| 재현 조건 | 기대 결과 |
|---|---|
| A 세션 만료/탈퇴 → 빈 계정 B 로그인 | B 목록은 빈 배열, 자동 POST 없음 |
| A 목록 조회 지연 → 로그아웃/B 로그인 → A 응답 도착 | B 목록·동기화 상태·pending 불변 |
| A 변경 요청 → B의 같은 종목 변경 → A finally 도착 | B pending 해제 안 됨 |
| 두 컴포넌트에서 같은 종목 빠르게 클릭 | 요청 1개, 성공 후 별/숫자 일치 |
| 추가 4xx / 응답 소실 / 저장 성공 후 count만 실패 | 각각 거절 안내 / 재동기화 / 성공한 별 유지와 집계 재시도 |
| 종목 X 응답 소실, Y 변경 진행 중 | Y 완료를 기다린 뒤 목록 조회, 그 사이 신규 변경 차단 |
| 오래된 count 조회 → 변경 성공 → 새 count 완료 → 오래된 응답 | 새 count 유지 |
| 동일 회원/종목 동시 POST | 행 1개, 둘 다 성공, 감사 필드 유효 |
| 무인증 count/list/POST/DELETE | count만 성공, 나머지 거부 |
| 존재하지 않는 종목 추가, 잘못된 stockName | 404/400, 정상 성공으로 숨기지 않음 |

프론트 테스트 도구는 현재 설정 확인 후 최소한으로 정한다. 상태 경합은 지연 Promise를 제어하는 테스트로 검증하고, DB 원자성은 PostgreSQL 통합/동시성 테스트로 검증한다. 실행한 동시성 테스트만 `server/BENCHMARK.md`에 방법·명령·실측 결과를 기록한다. 아직 어떤 테스트도 실행하지 않았다.
